# План улучшения MarkD и автоматических обновлений

Дата: 20 сентября 2026. Основание: [аудит MarkD 0.4.0](2026-09-20-markd-audit.md). Целевые платформы: macOS и Windows.

Порядок работ: надёжное сохранение → ежедневные сценарии → воспроизводимый выпуск → автообновление → улучшения по измерениям. Первый результат должен устранить риски потери данных, а не увеличивать число функций.

## 1. Безопасная сессия документа

Закрывает F01–F03. Ориентир: 2–4 рабочих дня разработки и проверки, после уточнения реализации.

- Ввести единый flush незавершённого ввода. Save/Save As/PDF и переходы сначала фиксируют активные поля, затем читают актуальный store. Ввод IME не теряется.
- Хранить ревизию документа и ревизию подтверждённого сохранения; не сбрасывать dirty безусловно. Отмечать, какому документу и snapshot принадлежит асинхронная операция.
- Реализовать общий `requestCloseDocument(reason)` для закрытия окна, выхода, нового/открываемого проекта и установки обновления.
- Предлагать «Сохранить», «Не сохранять», «Отмена». Cancel, ошибка записи и отмена Save As оставляют документ открытым. Повторные команды не запускают конкурирующие операции.
- Добавить локальные recovery snapshots, сохраняемые после изменений с debounce и ограничением частоты. При старте предложить восстановление; оригинал `.markd` не перезаписывать без обычного Save. Определить очистку старых черновиков и поведение для больших ресурсов.
- При аварии renderer использовать последний recovery snapshot; не обещать восстановление символов, ещё не дошедших до recovery. Показать время сохранённого черновика.
- Усилить файловую запись: тестировать сбой rename, заполненный диск, read-only каталог и восстановление `.bak`. Сохранять рабочую копию до подтверждённой замены.

**Приёмка:** последние символы присутствуют после немедленного Save и повторного открытия; изменение во время Save остаётся dirty; завершение Save старого документа не меняет новый; закрытие/выход нельзя продолжить после Cancel или ошибки; аварийный перезапуск предлагает recovery. Проверить macOS и Windows, включая закрытие во время записи.

## 2. Команды, страницы и понятное состояние

Закрывает F04–F06 и основные неудобства. Ориентир: 2–4 дня.

- Общий реестр команд для native menu, toolbar и клавиатуры. Сохранить привычное редактирование текста и маршрутизировать объектную историю отдельно.
- Ввести `activePageId`, выбор страницы с мыши/клавиатуры и добавление на неё. Различать страницу проекта и автоматически созданное продолжение таблицы.
- Подключить управление страницами, включая уже существующие duplicate/move; удаление страницы добавить с Undo и защитой последней страницы.
- Сбрасывать preview/selection/operation при переходе к другому документу.
- Основная кнопка «Сохранить» выполняет Save; отдельное меню содержит Save As, копию и шаблон. Добавить «Показать файл».
- Общий статус сохранения и ошибок виден и озвучивается в edit/preview; ошибки дают следующий шаг и возможность повтора.
- «По ширине» / «Вся страница», сворачивание панели свойств, переход к объекту из дерева.
- Шаблоны открываются как новые документы; стартовый экран различает пустой документ и КП.

**Приёмка:** Ctrl/Cmd+Z работает для добавления, удаления и перемещения; не ломает ввод текста. Добавление на второй лист действительно изменяет второй лист. После New/Open доступно редактирование. Работа клавиатурой сохраняет фокус. При ширине 1024 px доступны все команды и удобный масштаб страницы.

## 3. Проверяемая доставка macOS и Windows

Закрывает F07 и пробелы тестирования. Ориентир: 1–3 дня без получения сертификатов и внешних учётных записей.

- Зафиксировать CI на Node из `.nvmrc`; `npm ci`, typecheck, lint, unit и E2E.
- Заменить `/private/tmp` на уникальные temp-каталоги; положить маленькое тестовое изображение в репозиторий вместо пути в macOS. Убрать зависимость тестов от личных данных пользователя.
- Исправить путь macOS x64. Собирать macOS arm64 и x64; Windows x64 NSIS. Windows arm64 включать после явного решения о поддержке.
- Разделить локальную ad-hoc `.app` и production-release конфигурации. В production не выполнять повторное `codesign --sign -` поверх Developer ID подписи.
- Запускать smoke установленного приложения на macOS/Windows и несколько ключевых сценариев через production renderer, а не только Vite.
- Добавить визуальные проверки PDF/страниц с отдельными baseline для ОС. Проверять реальные страницы PDF, шрифты и отсутствие обрезанного содержимого.
- Обновить README: версия Node, местоположение логов/черновиков, переносимость `.markd`, команды Save/Save As и различие local package/release.

**Приёмка:** чистая CI-машина получает воспроизводимые артефакты; приложение запускается, открывает существующий проект, сохраняет и экспортирует PDF на обеих ОС.

## 4. Как обновлять без ручного скачивания установщика

Это возможно в текущем Electron-приложении. Пользователь один раз устанавливает сборку со встроенным механизмом обновления. После этого MarkD сам проверяет версию, скачивает пакет в фоне и предлагает «Перезапустить и обновить».

Скачивание данных всё равно происходит. На Windows updater может незаметно скачать и запустить NSIS-пакет; пользователь не ищет его на сайте. Дифференциальное скачивание может уменьшить трафик, но иногда нужен полный пакет. Обещать обновление без перезапуска или всегда маленький размер загрузки нельзя.

Нынешняя 0.4.0 не содержит updater, поэтому доставить в неё первый updater этим же отсутствующим механизмом нельзя. Нужна **одна ручная переходная установка**. Администрируемая доставка через MDM могла бы заменить её, но такой инфраструктуры в проекте не обнаружено.

### Выбор механизма

Предлагается **electron-updater + существующий electron-builder**. Windows уже использует NSIS; смена системы упаковки для этого не требуется. Достаточно статического HTTPS-хранилища артефактов и metadata либо GitHub Releases. Официальный путь для NSIS и macOS описан в [руководстве electron-builder ветки 26](https://github.com/electron-userland/electron-builder/blob/v26.0.12/pages/auto-update.md).

Встроенный `autoUpdater` из `electron` и пакет `electron-updater` имеют разные контракты. Для существующей NSIS-сборки план относится ко второму. [Документация Electron](https://www.electronjs.org/docs/latest/tutorial/updates) описывает также Squirrel-варианты; их конфигурацию не следует смешивать с NSIS.

В проекте закреплён builder 26.15.3; updater пока отсутствует. Перед реализацией выбрать и закрепить совместимый стабильный updater, сверить API по установленным типам и проверить пару версий на реальной установке. Context7 выдал преимущественно документацию v27; для различий API дополнительно проверены официальные исходники ветки 26. Точная документация тега 26.15.3 в используемом источнике не получена. Не копировать конфигурацию v27 в проект v26 и не считать переход на v27 условием автообновления.

Для ветки updater 6 используются `autoInstallOnAppQuit` и позиционные параметры `quitAndInstall`; новая ветка меняет этот контракт. См. [AppUpdater ветки 26](https://github.com/electron-userland/electron-builder/blob/v26.0.12/packages/electron-updater/src/AppUpdater.ts) и [BaseUpdater](https://github.com/electron-userland/electron-builder/blob/v26.0.12/packages/electron-updater/src/BaseUpdater.ts). При закреплении иной версии заново сверить API. Существующий `electron-builder-v27-migration.md` сохраняет отдельный migration gate.

### Сервер обновлений

| Вариант | Применение | Что нужно |
| --- | --- | --- |
| Generic HTTPS + объектное хранилище/CDN | Рекомендуемая исходная схема для независимого распространения | Постоянный URL, загрузка release-артефактов CI, корректный кеш и Range requests |
| GitHub Releases | Простой вариант, если бинарники можно публиковать открыто | Репозиторий релизов, CI publishing, проверка доступности пользователям |
| Собственный авторизованный feed | Если скачивания должны быть закрытыми | Пользовательская авторизация, краткоживущие права и поддержка сервиса |

Исходники могут оставаться закрытыми при открытой раздаче бинарников. Нельзя зашивать общий GitHub token, S3 secret или ключ подписи в приложение. Домен/провайдер пока не выбран; схема не требует покупки или публикации на этапе этого плана.

Для generic provider CI загружает артефакты самостоятельно. Предлагаемое разделение feeds:

```text
updates/stable/mac/arm64/    latest-mac.yml + versioned ZIP/DMG + generated blockmaps
updates/stable/mac/x64/     latest-mac.yml + versioned ZIP/DMG + generated blockmaps
updates/stable/win/x64/     latest.yml     + versioned NSIS EXE + generated blockmaps
updates/beta/...            отдельный тестовый канал
```

Это предлагаемая структура, не существующий адрес. URL нужной платформы/архитектуры должен попадать в packaged `app-update.yml`. Metadata берётся из builder, не пишется вручную. Сначала загрузить все файлы версии и проверить хеши/доступность, затем опубликовать channel metadata. Артефакты версии неизменяемы; metadata имеет короткий cache TTL. Старые blockmaps и пакеты сохраняются для поддерживаемого пути обновления; при невозможности differential download допускается полный пакет.

### Требования к пакетам

| Платформа | Сейчас | Для production-обновлений |
| --- | --- | --- |
| macOS | `target: dir`, `identity: '-'`, hardened runtime выключен, повторная ad-hoc подпись в скрипте | Developer ID Application, hardened runtime с проверенными entitlements, notarization; DMG для начальной установки и ZIP для updater; arm64/x64 |
| Windows | NSIS x64, auto-discovery подписи выключен | Сохранить NSIS и стабильную идентичность приложения; настроить production signing, проверку подписи и тест обновления существующей установки |

macOS требует подписанного приложения для поддерживаемого пути автоматического обновления; ZIP нужен Squirrel.Mac внутри этого механизма. Текущая ad-hoc подпись не заменяет Developer ID процесс распространения. Notarization нужна для нормального распространения через Gatekeeper; подробности — [официальное руководство Electron по подписи](https://www.electronjs.org/docs/latest/tutorial/code-signing).

На Windows отсутствие сертификата не означает, что NSIS технически вообще не может обновляться. Однако для production-плана требуется доверенная подпись и проверка издателя; SmartScreen/reputation и переход с существующей неподписанной установки проверить отдельно. Сохранить `appId` и правила установки, не менять их одновременно с внедрением обновлятора. Проверить install scope, права каталога и необходимость UAC.

### Поведение внутри приложения

Предлагаемый сценарий: проверка после готовности приложения и затем с умеренным интервалом → фоновая загрузка → постоянное сообщение «Готова версия X» с действиями «Что нового», «Перезапустить и обновить», «Позже» → безопасное завершение сессии → установка.

- `updateService` работает в main только для packaged builds. Dev/E2E не обращаются к production-feed.
- Состояния: `idle`, `checking`, `available`, `downloading`, `downloaded`, `installing`, `error`. Повторные запросы объединяются; подписки не дублируются при пересоздании окна.
- Узкий типизированный preload/IPC: получить статус, проверить, скачать, установить, подписаться на изменения. Проверять отправителя и payload так же, как у остальных IPC.
- Ручная команда «Проверить обновления» и окно «О программе» с версией. Ошибка сети не блокирует редактирование и не вызывает модальные окна при каждом старте.
- Все update-события и ошибки записываются существующим logger. Release notes отображаются как текст или безопасный формат, без произвольного HTML.
- Не устанавливать автоматически во время работы. В выбранной версии updater явно настроить политику установки. Для updater 6 отключить автоматическую установку на quit и вызывать установку через контролируемый сценарий; для другой major проверить соответствующий API.
- **До** вызова `quitAndInstall` выполнить flush полей и весь протокол сохранения из этапа 1. Нельзя рассчитывать, что обычный close-dialog после вызова updater успеет защитить данные.
- «Позже» сохраняет доступность обновления, работа продолжается. При следующем запуске повторно проверить применимость пакета; не переустанавливать отозванную или устаревшую версию.
- Схема `.markd` не меняется только ради обновлятора. Миграции отдельно тестируются на реальных старых файлах. Проблемный выпуск заменяется исправленной версией с большим номером; автоматический downgrade по умолчанию не нужен.

### Release pipeline

```mermaid
flowchart LR
    A[Тег версии] --> B[Проверки macOS и Windows]
    B --> C[Сборка и подпись]
    C --> D[Notarization macOS]
    D --> E[Проверка установленных пакетов]
    E --> F[Загрузка файлов версии]
    F --> G[Публикация metadata]
    G --> H[MarkD скачивает обновление]
    H --> I[Сохранение документа]
    I --> J[Перезапуск и установка]
```

Подпись Windows и macOS выполняется соответствующими jobs. Diagram показывает обязательные ворота выпуска, а не требование выполнять все задачи последовательно в одном runner.

Ориентир на updater и интеграцию: 2–4 дня после готовности этапов 1 и 3, сертификатов и feed. Получение сертификатов, доступов и проверки на пользовательских машинах в эту оценку не входят.

### Проверка обновления N → N+1

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Установленная подписанная версия N, доступна N+1 | Фоновая загрузка, корректная версия после перезапуска, проекты и профиль сохранены |
| macOS arm64 и x64 / Windows x64 | Клиент получает артефакт своей платформы и архитектуры |
| Несохранённый документ, включая последние введённые символы | Save фиксирует данные; Cancel оставляет приложение открытым |
| Ошибка сохранения или отмена выбора пути | Установка не начинается |
| Нет сети / 404 / повреждённый metadata | Редактор работает, ошибка понятна, доступен повтор |
| Обрыв загрузки / неправильный checksum / неверная подпись | Не устанавливается непроверенный пакет; retry безопасен |
| Недостаток диска / запрет записи / Windows UAC | Понятная ошибка; нет заявления об успешном обновлении |
| ОС завершает сеанс | Не запускать опасную конкурирующую установку; отдельно проверить политику выбранной версии updater |
| «Позже», повторный старт, два запроса проверки | Нет дублирующейся загрузки/установки и принудительного закрытия документа |
| Старые .markd и .kpdoc после обновления | Открываются, сохраняются и дают ожидаемый PDF |
| Отозванный релиз / старый metadata из кеша | Нет установки непредусмотренной версии; выпуск исправления большим semver |
| Первая переходная установка поверх 0.4.0 | Сохраняются данные, ассоциация файлов, профиль и ожидаемый путь установки |

Завершением этапа считается обновление двух реально установленных подписанных версий на обеих ОС. Mock-события updater и успешный `npm run build` этот критерий не заменяют.

## 5. Целостность и масштабирование

- Закрыть F08: уникальные ID, декодируемость изображений, понятные коды ошибок.
- Ограничивать чтение файла до его загрузки в память; профилировать большие `.markd` и тяжёлые таблицы.
- Разделять данные документа, историю и состояние интерфейса; уменьшать полное копирование по результатам измерений.
- Добавить визуальный контроль шрифтов, таблиц, переносов и PDF по каждой ОС.
- ZIP-контейнер вместо JSON/base64 рассматривать только при регулярном достижении лимита 64 МиБ. Это отдельная миграция формата, не условие запуска автообновлений.

## Решения, необходимые перед внешним выпуском

Требуется определить место раздачи бинарников и постоянный feed URL, владельца сертификатов macOS/Windows, публичность загрузок и доступные CI runners. Потребуется подтвердить поддерживаемые версии ОС и наличие пользователей Intel Mac. Эти вопросы не мешают начать исправление данных и UX; секреты должны настраиваться в CI, а не передаваться через исходники или документы.

Первым небольшим выпуском изменений рекомендуется этап 1 с regression-тестами. До его приёмки подключать автоматический перезапуск приложения к updater преждевременно.

## Уточнение способа распространения

Владелец выбрал GitHub Releases. Описанный выше generic HTTPS feed заменён публичным GitHub provider; отдельный сервер не требуется. Актуальные каналы архитектур, workflow создания draft и порядок публикации описаны в [руководстве выпуска](../releasing.md).
