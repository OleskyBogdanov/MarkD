# План: хранилище Markd, переносимые макеты, слои, стили и журнал аварий

Дата: 2026-09-01

## Цель

Сделать сохранение проектов предсказуемым и переносимым, добавить полноценную модель слоёв и настройки оформления элементов, а также обеспечить диагностику сбоев до и после запуска Electron.

## Что уже есть в проекте

- Electron main/preload/renderer с изолированным renderer и типизированным IPC.
- Самодостаточный файл `.kpdoc`: проект хранится как JSON, а изображения уже встраиваются как `data:`-ресурсы.
- Zod-схема с `schemaVersion = 2` и миграцией версии 1.
- Атомарная запись проекта через временный файл и `rename`.
- Плоский список `page.elements`; порядок задаётся `zIndex`, но понятия слоя пока нет.
- Цвета уже есть у `textField` и `selectField`, но не доступны полностью в UI; у обычного текста нет цвета, у таблицы нет модели стилей.
- Выравнивание есть у обычного текста и текстового поля, но у таблицы отсутствует.
- Ошибки открытия/сохранения/экспорта превращаются в общие сообщения; исходная ошибка и stack trace не сохраняются.

## Результат расследования текущего вылета

В системных отчётах macOS от `2026-09-01 17:40:08` и `17:41:13` зафиксирован запускной сбой `DYLD / Library missing`: бинарник Electron не нашёл `Electron Framework.framework/Electron Framework` внутри `node_modules/electron/dist/Electron.app`. Процесс завершился ещё до запуска `src/main/main.ts`, поэтому обычный обработчик ошибок приложения такой сбой поймать не мог.

Сейчас framework уже присутствует в `node_modules` (файлы появились позднее, около 17:43). Это согласуется с неполной/прерванной установкой либо восстановлением зависимости, но точную причину исчезновения файла по имеющимся отчётам установить нельзя.

Отдельно текущая packaged-сборка не проходит smoke-запуск, а `codesign --verify --deep --strict` сообщает отсутствие ресурсов подписи (`_CodeSignature`). Поэтому в план включена отдельная проверка целостности dev-runtime и подписи packaged-приложения.

## Зафиксированные проектные решения

1. Внутреннее хранилище использует стандартный Electron-путь `app.getPath('userData')` (`~/Library/Application Support/kp-editor-macos` в текущей macOS-сборке). Проекты, PDF и журналы разнесены по `projects`, `exports` и `logs`.
2. Диалог «Сохранить как» по умолчанию открывается в каталоге `projects`, но открыть или сохранить переносимый файл можно и в другом месте.
3. `.kpdoc` остаётся одним самодостаточным JSON-файлом без абсолютных путей. Это минимально рискованно для текущего кода и уже подходит для копирования/отправки. Логический формат отделяется от файлового I/O, чтобы позднее его можно было завернуть в ZIP или отправлять на сервер без переделки редактора.
4. Слои принадлежат всему проекту, а каждый элемент страницы содержит `layerId`. Так один набор «Фон / Контент / Изображения» одинаково работает на всех страницах.
5. Активный слой — состояние редактора, а порядок, имя, видимость и блокировка слоёв — часть переносимого проекта.
6. Запрет редактирования чужого слоя проверяется и в UI, и в store. Одного `pointer-events: none` недостаточно, поскольку команды меню и программные вызовы тоже могут изменить элемент.
7. Для таблиц приоритет выравнивания: настройка строки → настройка колонки → значение всей таблицы. Это даёт понятный ответ при пересечении выбранной строки и колонки.

## Целевая структура данных (`schemaVersion = 3`)

```ts
type KpLayer = {
  id: string;
  name: string;
  order: number;
  visible: boolean;
  locked: boolean;
};

type KpProjectV3 = {
  schemaVersion: 3;
  metadata: {
    id: string;
    title: string;
    createdBy?: string;
    createdAt: string;
    updatedAt: string;
  };
  layers: KpLayer[];
  pages: KpPage[];
  assets: KpAsset[];
  // остальные существующие поля
};

type CommonElementFields = {
  layerId: string;
  zIndex: number; // порядок только внутри слоя
};

type TextStyle = {
  // существующие поля
  color: string;
};

type TableStyle = {
  textColor: string;
  backgroundColor: string;
  headerTextColor: string;
  headerBackgroundColor: string;
  borderColor: string;
  align: 'left' | 'center' | 'right';
  columnAlign: Record<string, 'left' | 'center' | 'right'>;
  rowAlign: Record<string, 'left' | 'center' | 'right'>;
};
```

Миграция v1/v2 создаёт один слой `Основной`, назначает его всем существующим элементам, добавляет безопасные цвета по умолчанию и стиль таблицы. Исходный файл не переписывается при открытии; v3 записывается только при следующем сохранении.

## Этап 1. Папка Markd и единая файловая инфраструктура

### Изменения

- Создать `src/main/storage/markdPaths.ts`:
  - вычислять путь через `app.getPath('userData')`, не через Documents или захардкоженный `/Users/...`;
  - идемпотентно создавать `projects`, `exports` и `logs` через `mkdir(..., { recursive: true })`;
  - возвращать `projectsRoot`, `logsRoot` и безопасный путь по умолчанию для файла.
- В `src/main/ipc/ipcHandlers.ts` задавать `defaultPath: join(projectsRoot, safeProjectName + '.kpdoc')` для Save As.
- Сохранить возможность открытия `.kpdoc` из любой папки.
- Нормализовать имя файла из названия проекта: удалить запрещённые символы, ограничить длину, иметь fallback `proposal-<timestamp>`.
- Оставить атомарную запись, но вынести её в тестируемый файловый сервис и обеспечить создание родительского каталога.

### Критерии приёмки

- При первом запуске в `userData` появляются каталоги `projects`, `exports` и `logs`.
- Повторный запуск не удаляет и не перезаписывает существующие файлы.
- Первый Save As предлагает папку Markd.
- Пользователь всё ещё может открыть/сохранить проект вне папки Markd.

## Этап 2. Переносимый формат проекта и миграция v3

### Изменения

- Обновить `src/shared/projectSchema.ts` и реэкспорты в `src/renderer/domain/model.ts`.
- Разделить:
  - `serializeProject` / `migrateProject` — чистая работа с логической моделью;
  - `projectFileService` в main — чтение, лимиты, атомарная запись.
- Гарантировать, что проект не содержит `file://` и абсолютных путей; все используемые изображения должны находиться в `assets` как `data:`.
- Добавить проверку ссылочной целостности:
  - каждый `image.assetId` существует;
  - каждый `element.layerId` существует;
  - `selectedOptionId` существует либо равен `null`;
  - таблица не содержит ссылок на удалённые строки/колонки в style-map.
- Исправить конфликт лимитов: сейчас импорт разрешает изображение до 25 МБ, а весь проект — только 16 МБ. Для JSON-MVP установить согласованный бюджет (например, проект 64 МБ, изображение 12 МБ) и проверять размер уже после base64-кодирования.
- Добавить `updatedAt` при успешном сохранении, не при каждом движении элемента.
- Сохранить чтение v1 и v2; добавить фикстуры миграции и round-trip `open → save → move file → open`.

### Критерии приёмки

- Один `.kpdoc` можно скопировать на другой путь/компьютер и открыть без исходных картинок.
- v1 и v2 открываются без потери элементов, затем сохраняются как v3.
- Неизвестная будущая версия выдаёт понятную ошибку и попадает в лог.
- Ошибка превышения размера сообщает фактический лимит до потери пользовательских данных.

## Этап 3. Полноценные слои

### Модель и store

- Добавить в `EditorState` `activeLayerId` и операции:
  - `addLayer`, `renameLayer`, `deleteLayer`;
  - `reorderLayer`, `setLayerVisibility`, `setLayerLocked`;
  - `setActiveLayer`, `moveElementToLayer`.
- Новые элементы всегда создаются в активном, видимом и разблокированном слое.
- Удаление непустого слоя требует явного решения в UI: перенести элементы в другой слой либо удалить вместе со слоем. По умолчанию — перенос в ближайший слой.
- При переключении слоя сбрасывать выделение элемента из другого слоя и завершать drag/resize.
- Все mutating actions (`updateText`, `updateElementRect`, таблицы, delete и т. п.) вызывают общий guard `canEditElement(state, pageId, elementId)`.
- Undo/Redo включает изменения структуры слоёв, их порядка и перенос элементов.

### UI и renderer

- Создать `LayersPanel` в правой панели рядом с Inspector:
  - активный слой;
  - создание, переименование, удаление;
  - drag-and-drop/кнопки изменения порядка;
  - видимость и блокировка;
  - количество элементов;
  - перенос выделенного элемента в выбранный слой.
- В `ProjectCanvas`:
  - сортировать сначала по `layer.order`, затем по `element.zIndex`;
  - не рендерить скрытые слои в edit/preview/print;
  - для неактивных или заблокированных слоёв запретить фокус, selection, ввод, drag и resize;
  - передавать `interactive` в `ElementFrame`, а не размазывать условие по каждому renderer.
- Кнопки Delete и инспектор отключаются для элементов неактивного/заблокированного слоя.

### Критерии приёмки

- Элемент другого слоя нельзя выделить, редактировать, переместить, изменить через Inspector или удалить горячей клавишей.
- Переключение активного слоя немедленно меняет доступность элементов.
- Порядок и видимость одинаковы в редакторе, preview и PDF.
- Слои и принадлежность элементов сохраняются в `.kpdoc` и восстанавливаются после открытия.

- Валидировать цвета общей Zod-схемой (`#RRGGBB` и при необходимости `#RRGGBBAA`), не принимать произвольный CSS.
- Обычный текст: `style.color` в схеме, store, Inspector и `TextElementRenderer`.
- Текстовое поле и select: вывести уже существующие `textColor`, `labelColor`, `backgroundColor`, `borderColor` в Inspector.
- Таблица: добавить и применить `textColor`, `backgroundColor`, `headerTextColor`, `headerBackgroundColor`, `borderColor`.
- Фон страницы: заменить свободное текстовое поле цвета на тот же `ColorControl`.
- Убрать соответствующие жёстко заданные цвета из `styles.css`, оставив CSS custom properties с безопасными fallback.

### Критерии приёмки

- Изменение цвета создаёт одну понятную запись в Undo, а ввод в HEX-поле не засоряет историю промежуточными невалидными значениями.

## Этап 6. Журналирование, диагностика и защита от повторения вылета

### Файловый логгер

- Создать `src/main/logging/appLogger.ts`, писать JSONL в `<userData>/logs/markd-YYYY-MM-DD.log`.
- Поля записи: timestamp, level, process (`main`/`renderer`/`launcher`), event, message, stack, appVersion, Electron/Node/macOS version, pid, exitCode/reason, projectPath только после маскирования домашней части.
- Не писать содержимое документа, текст таблиц, base64-картинки и другие пользовательские данные.
- Ротация: ограничение размера одного файла и хранение, например, 14 последних файлов.

### События после старта main

- Подключить `process.on('uncaughtException')` и `process.on('unhandledRejection')` до создания окна.
- Подписать каждое окно на `render-process-gone`, `unresponsive`, `did-fail-load` и неожиданный `closed`.
- Подписать `app` на `child-process-gone`.
- Добавить renderer Error Boundary и обработчики `window.error`/`unhandledrejection`; передавать структурированную ошибку в main через строго валидируемый IPC-канал.
- В существующих `catch` логировать исходную ошибку до показа безопасного сообщения пользователю.
- Добавить пункт меню «Показать папку с журналами» и отображать путь к последнему логу в сообщении после восстановления.

### Сбои до старта main — конкретно текущий случай

- Добавить `scripts/run-electron.mjs`, который до запуска Electron:
  - проверяет существование исполняемого файла и `Electron Framework.framework`;
  - при отсутствии пишет причину в `<userData>/logs/launcher-YYYY-MM-DD.log` обычным Node;
  - завершает работу с инструкцией `npm ci`/переустановки зависимости вместо немого исчезновения.
- Перевести `npm run dev` и E2E-launch helper на этот preflight либо использовать общую функцию проверки runtime.
- В `package:mac` после сборки выполнять:
  - наличие Frameworks и `app.asar`;
  - `codesign --verify --deep --strict`;
  - smoke-запуск упакованного бинарника.
- Не публиковать/не считать сборку успешной, если подпись или smoke-проверка не прошли.
- При необходимости выполнять явную ad-hoc подпись всех вложенных helper/framework и корневого `.app`, затем повторять `codesign --verify`.

### Критерии приёмки

- Ошибка main/renderer после старта оставляет stack trace в `Markd/logs`.
- Падение renderer оставляет reason/exitCode и приложение может показать экран восстановления или пересоздать окно.
- Отсутствующий Electron Framework фиксируется launcher-логом даже до старта main.
- Сборка с отсутствующей/повреждённой подписью блокируется CI/smoke-проверкой.
- В логи не попадает содержимое проекта.

## Этап 7. Тесты и выпуск

### Unit/integration

- `projectSchema`: v1 → v3, v2 → v3, round-trip v3, неизвестная версия, битые layer/asset/style references.
- Store: CRUD слоёв, guards активного/locked/hidden слоя, перенос элемента, Undo/Redo.
- Таблица: приоритет row/column/table, очистка style-map после удаления.
- Storage/logger: временный `userData` root через dependency injection, создание каталогов, атомарная запись, ротация и redaction.

### E2E

- Первый запуск и Save As в Markd.
- Сохранить проект с картинкой, переместить `.kpdoc`, открыть и сравнить содержимое/preview.
- Два слоя: убедиться, что чужой слой нельзя редактировать ни мышью, ни клавиатурной командой.
- Цвета текста/таблицы и выравнивание строки/колонки после reopen и в PDF.
- Искусственный renderer exception создаёт запись в логе.
- Повреждённый/отсутствующий Electron Framework приводит к launcher-логу и ненулевому exit code.
- Packaged smoke обязательно включает `codesign --verify` перед Playwright.

### Порядок выпуска

1. Storage paths + logger + preflight/packaging checks.
2. Схема v3 и миграции, без нового UI.
3. Layers model/store/renderer, затем LayersPanel.
4. Цветовые controls и стили элементов.
5. Выравнивание таблицы.
6. Полный E2E, ручная проверка PDF и тест открытия копии `.kpdoc` на чистом профиле.

Каждый этап должен оставлять приложение собираемым и сохранять чтение старых документов. Нельзя объединять миграцию формата, большой UI-рефакторинг и исправление упаковки в один релиз без промежуточных проверок.

## Риски и способы снижения

- **Потеря совместимости:** только явные миграции v1/v2 → v3 и фикстуры реальных документов.
- **Слишком большие JSON-файлы:** согласовать лимиты сейчас; при росте перейти на ZIP-контейнер, не меняя логический manifest.
- **Обход ограничений слоя:** единый store guard плюс UI-disable, тесты команд меню и Undo/Redo.
- **Неоднозначность row/column align:** закрепить и протестировать приоритет «строка → колонка → таблица».
- **Лог не создаётся при loader crash:** отдельный Node-launcher до Electron и packaging integrity check.
- **Утечка данных в лог:** structured allowlist полей, redaction путей, запрет snapshot/base64 в payload логгера.

## Definition of Done

- Все шесть пользовательских требований покрыты автоматизированными тестами.

- Перемещённый файл с изображениями открывается автономно.
- Слой реально изолирует редактирование на уровне store и UI.
- Цвета и выравнивание совпадают в edit, preview и PDF.
- При воспроизводимом JS/renderer сбое появляется понятный лог в `<userData>/logs`.
- Dev runtime и packaged app проходят preflight, проверку подписи и smoke-запуск.
